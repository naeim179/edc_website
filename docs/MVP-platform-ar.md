# وثيقة النسخة الأولى للمنصة التعليمية (MVP)

## 1. هدف النسخة الأولى

إطلاق منصة تعليمية بسيطة وقابلة للاستخدام تتيح للطالب إنشاء حساب، استعراض الدورات، شراء دورة، مشاهدة الدروس، ومتابعة تقدمه، مع لوحة تحكم أساسية لمدير المنصة.

---

## 2. أنواع المستخدمين

### الطالب

يستطيع الطالب:

- إنشاء حساب جديد.
- تسجيل الدخول والخروج.
- استعراض قائمة الدورات.
- فتح صفحة تفاصيل كل دورة.
- شراء دورة مدفوعة.
- الوصول إلى الدورات التي اشتراها.
- مشاهدة الدروس.
- تحديد الدرس كمكتمل.
- متابعة نسبة التقدم في الدورة.

### مدير المنصة (Admin)

يستطيع المدير:

- تسجيل الدخول إلى لوحة الإدارة.
- إضافة دورة جديدة.
- تعديل بيانات الدورة.
- حذف دورة.
- إضافة أقسام داخل الدورة.
- إضافة دروس داخل كل قسم.
- إضافة عنوان ووصف ورابط فيديو لكل درس.
- نشر الدورة أو إخفاؤها.
- مشاهدة قائمة الطلاب.
- مشاهدة الطلبات والمدفوعات.
- تسجيل طالب في دورة يدويًا.
- إلغاء وصول طالب إلى دورة عند الحاجة.

> في النسخة الأولى، لا يوجد حساب مستقل للمدرّس. مدير المنصة هو المسؤول عن إدارة جميع الدورات.

---

## 3. رحلة الطالب الأساسية

1. يدخل الطالب إلى الموقع.
2. ينشئ حسابًا جديدًا أو يسجل الدخول.
3. يستعرض الدورات المتاحة.
4. يفتح صفحة تفاصيل الدورة.
5. يضغط على زر شراء الدورة.
6. ينتقل إلى صفحة الدفع التابعة لمزود الدفع.
7. بعد تأكيد الدفع، يُسجّل الطالب في الدورة.
8. تظهر الدورة في صفحة "دوراتي".
9. يفتح الطالب الدورة ويشاهد الدروس.
10. يحفظ النظام الدروس المكتملة ونسبة التقدم.

---

## 4. الصفحات المطلوبة

### الصفحات العامة

- الصفحة الرئيسية.
- صفحة قائمة الدورات.
- صفحة تفاصيل الدورة.
- صفحة تسجيل الدخول.
- صفحة إنشاء حساب.
- صفحة نسيت كلمة المرور.
- صفحة من نحن.
- صفحة تواصل معنا.
- صفحة الشروط والأحكام.
- صفحة سياسة الخصوصية.

### صفحات الطالب

- لوحة الطالب.
- صفحة دوراتي.
- صفحة مشاهدة الدورة.
- صفحة مشاهدة الدرس.
- صفحة الملف الشخصي.
- صفحة الطلبات والمدفوعات.

### صفحات الإدارة

- لوحة التحكم الرئيسية.
- إدارة الدورات.
- إضافة دورة.
- تعديل دورة.
- إدارة أقسام ودروس الدورة.
- إدارة الطلاب.
- إدارة التسجيلات في الدورات.
- إدارة الطلبات والمدفوعات.

---

## 5. وظائف الدورات

كل دورة تحتوي على:

- عنوان.
- صورة رئيسية.
- وصف مختصر.
- وصف كامل.
- السعر.
- حالة النشر: منشورة أو مخفية.
- أقسام.
- دروس.
- رابط فيديو لكل درس.
- ملفات مرفقة اختيارية.
- ترتيب للأقسام والدروس.

---

## 6. وظائف الدفع

في النسخة الأولى:

- الدفع يكون مرة واحدة لكل دورة.
- يتم إنشاء طلب بحالة `pending` قبل تحويل الطالب إلى بوابة الدفع.
- يتم تأكيد الدفع من خلال `Webhook` أو طلب موثوق من السيرفر.
- بعد نجاح الدفع تتحول حالة الطلب إلى `paid`.
- يتم إنشاء تسجيل للطالب في الدورة.
- لا يتم منح الطالب الوصول اعتمادًا على صفحة نجاح الدفع فقط.
- لا يتم تخزين أرقام البطاقات أو رمز CVV داخل المنصة.

حالات الطلب الأساسية:

- `pending`
- `paid`
- `failed`
- `cancelled`
- `refunded`

## 8. قواعد الصلاحيات

- الطالب لا يستطيع دخول لوحة الإدارة.
- الطالب لا يستطيع مشاهدة دورة مدفوعة قبل التسجيل فيها.
- جميع عمليات الإدارة تُنفذ من السيرفر بعد التحقق من صلاحية المستخدم.
- لا يتم الاعتماد على إخفاء الأزرار في الواجهة كوسيلة حماية.
- عمليات إنشاء الطلبات وتأكيد الدفع ومنح الوصول تتم من السيرفر.
- المفاتيح السرية لا تُحفظ داخل كود الواجهة أو GitHub.
- كل طلب API حساس يجب أن يتحقق من المستخدم وصلاحيته.

---

## 9. الأشياء المؤجلة إلى ما بعد النسخة الأولى

لا تشمل النسخة الأولى:

- تطبيق موبايل.
- حسابات مدرسين مستقلة.
- تعدد المدرسين داخل الدورة.
- بث مباشر.
- دردشة داخلية.
- شهادات.
- نظام نقاط أو شارات.
- اشتراكات شهرية.
- كوبونات.
- نظام تسويق بالعمولة.
- لغات متعددة.
- اختبارات متقدمة.
- واجبات وتصحيح يدوي.
- ذكاء اصطناعي داخل المنصة.
- حماية DRM متقدمة.
- Microservices.

---

## 10. معايير اكتمال النسخة الأولى

تعتبر النسخة الأولى جاهزة عندما:

- يستطيع الطالب إنشاء حساب وتسجيل الدخول.
- يستطيع المدير إضافة دورة وأقسام ودروس.
- يستطيع الطالب استعراض الدورة وشرائها.
- يتم تأكيد الدفع من السيرفر.
- يحصل الطالب على الوصول بعد الدفع فقط.
- يستطيع الطالب مشاهدة الدروس.
- يتم حفظ تقدمه.
- يستطيع المدير مشاهدة الطلبات والطلاب.
- تعمل المنصة على الهاتف والكمبيوتر.
- توجد نسخة احتياطية لقاعدة البيانات.
- توجد بيئة تجريبية قبل النشر للإنتاج.
- لا توجد مفاتيح سرية داخل المستودع.

---

## 11. تقسيم العمل بين أعضاء الفريق

### العضو الأول: الواجهة Frontend

- تحويل صفحات HTML إلى مكونات قابلة لإعادة الاستخدام.
- صفحات تسجيل الدخول والتسجيل.
- صفحات الدورات.
- لوحة الطالب.
- صفحة مشاهدة الدروس.
- التصميم المتجاوب.
- حالات التحميل والأخطاء.

### العضو الثاني: Backend وقاعدة البيانات

- تصميم قاعدة البيانات.
- تسجيل الدخول والصلاحيات.
- APIs الخاصة بالدورات والدروس.
- التسجيل في الدورات.
- حفظ تقدم الطالب.
- لوحة الإدارة.
- اختبارات الـAPI.

### العضو الثالث: الدفع والنشر والاختبار

- التواصل مع مزود الدفع.
- دمج صفحة الدفع.
- تنفيذ Webhooks.
- دمج استضافة الفيديو.
- إعداد GitHub.
- إعداد بيئات development وstaging وproduction.
- النسخ الاحتياطي والمراقبة.
- اختبار رحلة الطالب كاملة.

---

## 12. قواعد العمل داخل الفريق

- كل مهمة تُكتب في GitHub Issues أو لوحة مهام مشتركة.
- كل ميزة تُنفذ في Branch مستقل.
- لا يتم دمج أي Pull Request قبل مراجعته من عضو آخر.
- لا تُضاف ميزة جديدة للنسخة الأولى إلا بموافقة الفريق.
- لا يتم تنفيذ الدفع مباشرة على بيئة الإنتاج.
- يجب اختبار رحلة الطالب كاملة على بيئة staging.
- تحفظ المتغيرات السرية في Environment Variables.
- يجب توثيق كل API وكل جدول مهم.

---

## 13. أول مهام التنفيذ

1. إنشاء مستودع GitHub للمشروع.
2. رفع صفحات HTML الحالية.
3. إنشاء Branch باسم `development`.
4. اختيار التقنية النهائية للواجهة والـBackend.
5. رسم مخطط قاعدة البيانات.
6. تنفيذ التسجيل وتسجيل الدخول.
7. تنفيذ إدارة الدورات.
8. تنفيذ التسجيل اليدوي في الدورات.
9. تنفيذ مشاهدة الدروس وحفظ التقدم.
10. اختيار مزود الدفع وطلب حساب Sandbox.
11. تنفيذ الدفع على البيئة التجريبية.
12. اختبار النسخة الأولى مع عدد محدود من المستخدمين.

---

## 14. التقنية المقترحة مبدئيًا

- Frontend وBackend: Next.js + TypeScript.
- Database وAuthentication: Supabase.
- Hosting: Vercel.
- Video Hosting: Bunny Stream.
- Payments: مزود دفع يدعم بلد تسجيل المشروع.
- Source Control: GitHub.
- Environments: Development / Staging / Production.

> هذا الاختيار مبدئي، ويجب تثبيته بعد مراجعة خبرة أعضاء الفريق ومتطلبات بوابة الدفع.
